# 苏格拉底式文章编写

## 概述

本 skill 将"苏格拉底式问答法"与"文章写作"结合：用户以一个**问题或观点**开题，与模型进行一轮又一轮的提问、质疑、澄清，直到双方就核心概念达成共识；**当用户显式触发 `/synthesize` 时**，模型把这段思辨历程整理成一篇文章，写入本博客项目，供用户审查。

## 触发条件

当用户希望：
- 从一个问题/观点出发，进行深入思辨
- 通过与模型互相提问来澄清自己的想法
- 将讨论过程沉淀成一篇可供他人阅读的文章

时使用本 skill。若不涉及"探讨后成文"这一闭环，而只是单纯问答，则不要使用。

## 命令概览

思辨过程由三个显式命令驱动，各司其职：

- `/start-thinking` —— **启动思辨**：确立问题、开启苏格拉底式探讨（定义见 `.opencode/commands/start-thinking.md`）
- `/synthesize` —— 将已达成的共识落笔成文（定义见 `.opencode/commands/synthesize.md`）
- `/opinion-review` —— 启动 subagent 对思辨过程进行审查、指出问题并给出可能反驳（定义见 `.opencode/commands/opinion-review.md`）

## 核心工作流

### 阶段一：确立与提问（Ask）

由 `/start-thinking` 负责，遵循 `.opencode/commands/start-thinking.md`：

1. 请用户用**一个问题**或**一个观察/观点**开场。若用户只给了主题，用一两个问题帮其收敛成一个可辩的命题（Problem → Question）。
2. 用一句话复述你理解的问题，请用户确认，确保双方站在同一起点上。

### 阶段二：苏格拉底式探讨（Dialogue）

由 `/start-thinking` 开启并持续推进。反复进行"提问 → 回应 → 再追问"的循环，直到共识达成：

- **每次只抛一个核心追问**，避免一次抛出多个问题淹没用户。
- 追问要：
  - 揭示前提与假设（"为什么这样想？""它隐含了什么？"）
  - 指出矛盾或边界情况（"如果……会怎样？"）
  - 区分概念（"你指的是 A 还是 B？"）
  - 探询反例与另一面
- **认真对待用户的每一个回答**，顺着用户的思路提出下一个追问，而不是搬出一套预设。
- 控制深度：围绕主题的 3~6 个关键层面探讨即可，避免无休止发散。
- 观察用户何时开始**改述、补充、修正**自己的观点——那是共识逐渐形成的信号。
- **不明确的社会事实必须查证**：当讨论涉及现实世界的社会事实（如某项政策、统计数字、历史事件、特定概念/人物的主张、社会现象描述等）且你不确定其准确性时，**不要凭记忆臆断**，应使用 `web_search` 等搜索引擎工具查证核对，再基于查证结果继续探讨。若无法查到可靠来源，明确告知用户信息存疑。对"事实"与"观点/解释"也要区分——前者需要查证，后者属于思辨本身。

### 阶段三：达成共识（Synthesize）—— 由用户显式触发

- 当双方不再有新的分歧，用**一段话总结达成的共识**（论点 + 若干支撑子观点），并**等待**。
- **不要自行进入写作**。只有用户显式触发 `/synthesize` 或 `/opinion-review` 才继续后续步骤。
- 在用户触发之前，只停留在对话与共识阶段，不写文件。

### 阶段四：撰写文章（Write）

由用户触发 `/synthesize` 后执行。遵循 `.opencode/commands/synthesize.md` 的流程与本项目的文章格式（见下节"文章格式"）。

### 阶段五：审查（Review）

由用户触发 `/synthesize` 后执行。

- 创建后，**不要急于继续**，把用户给交给用户，请用户审查内容。
- 若用户要求修改，按反馈修订后 **始终在再次修改后运行 `npm run update-archive`**（因为时间/摘要可能变化）。
- 除非用户明确要求，不要提交 git。

## 文章格式

文章是**纯 HTML**，位于 `res/posts/<数字id>.html`。下一个可用 id 通过 `npm run create-post -- --title ...` 自动分配。务必遵循：

### 必需的 head 元数据块（`<blog>`）

放在 `<head>` 内，作为 `<meta name="description">` 之后：

```html
<blog>
  <author>作者名</author>
  <time>ISO时间字符串</time>
  <category>分类</category>
  <tag>标签一 标签二</tag>
</blog>
```

### 正文

- 正文写在 `<body>` 内的 `<article>` 里。
- 小节用 `<h1>`；段落用 `<p>`。
- 内容语言：**中文**（除非用户指定）。代码标识符用英文。
- **体裁：论证文/说理文**，而非苏格拉底式对话记录。**不要**把用户与模型的问答逐字还原成对话体。
- **叙述者视角：用户自己**。全文以"我"（即用户）的口吻立论、说理、得出主张，模型退居幕后、不出现。
- 思辨过程不靠"你问我答"呈现，而是以**层层递进的论证结构**展开：摆出问题 → 提出主张 → 论证 → 回应可能的反驳。
- 可引入**虚拟论敌**（strawman / 反方）来增强说理张力，但要用**自述、口语化**的口吻引出对立观点并加以回应，而非"有人也许会反对……"这类书面句式。贴合本博客文风，可用如"但，我们也考虑到……""话虽如此……""不过也有人说……"等自然过渡来带出反面考量。虚拟论敌仅是论述手法，不代表模型与用户的真实对话。

### 标准 boilerplate

每篇都需含 `@furryr/typescript-runtime` CDN script、`/static/js/index.tsx` script 与 `preload.css` link。**不要手写这些**——交给 `create-post` 脚本生成。

### 推荐的创建方式（必须）

> **强烈建议让 `npm run create-post` 生成骨架，而不是手写整个 HTML。**

因为 boilerplate 部分很长且容易出错，用 `npm run create-post` 的非交互模式（`--title` 触发）自动生成，然后用编辑工具替换/填充正文。

```bash
npm run create-post \
  --title "文章标题" \
  --description "摘要" \
  --author "作者" \
  --category "分类" \
  --tags "标签1 标签2" \
  --content "<h>小节标题</h><p>正文...</p>" \ # **强烈建议先使用空内容填充，再去阅读并修改创建的 HTML。**
```

- `--content` 为 `<article>` 内的 HTML 片段；多个小节用多个 `<h>/<p>` 拼接。
- 脚本默认会**自动更新归档**。如需先审阅再归档，可加 `--no-archive`，此时用户确认后需手动跑 `npm run update-archive`。
- 脚本会自动挑选下一个可用 id，无需手动指定。

### 归档（必做）

**每次创建/修改文章后必须运行 `npm run update-archive`**，否则 `res/archive.html` 索引不会反映变更（CI 部署时也会自动执行）。

## 写作建议

- 一篇好文章 = 一个清晰的问题 + 层层递进/收敛的论证 + 结尾回到原点给出回应。
- 用标题自然划分思辨的推进过程（如"问题"→"一个前提"→"反例"→"再界定"→"结论"）。
- 结论不要夸大：承认仍有未决之处，符合思辨而非说教的气质。
- 语言简洁、诚实、少用空洞修辞。

## 项目相关命令速查

- `npm run typecheck` / `npm run lint` —— 改代码后自检（文章是 HTML，通常不影响）
- `npm run update-archive` —— 重建归档索引
- `npm run create-post` —— 交互式向导；带 `--title` 时为非交互模式
