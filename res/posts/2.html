警告

在前端跑 Typescript 很好，那性能怎么办？
如果不需要极致的 geek style，我不建议你真的在自己的商务产品中原生跑 Typescript。

前言

非常喜欢 TypeScript 带来的鲁棒性，以及它的那个 JSX。

但是显然前端不加 bundler/tsc 是用不了的。tsc 速度比较神秘，加 webpack/tsup 的话我基于 JS 特性的 router/懒加载 就全毁了。

但是看着那个框架里的 Elements.p 又难受得要死。

嗯对，于是就考虑是否能在前端原生运行 Typescript/TSX。

先人

在运行 TS 这个方面，有两位先人存在，不过这两位实现的效果都一般般。

  • ECMAScript 的 Optional Static Typing 提案。显然，这玩意不支持 TSX，而且对于一些可擦除的 descriptor (private protected etc.) 支持也是几乎没有的。
  • ts-browser。兼容性不明，类型擦除基于正则，且 module resolution 非常有问题。

于是就只能自己写了。

尝试

由于使用 TSX 只需要做语法糖转换 + 类型擦除就可以了，我们可以通过打包一个 babel，然后使用 MutationObserver 监听 script tag 的插入从而实现实时转译 TypeScript 到 JavaScript。

对于转换后的代码，我们只需要生成一个 blob URL 然后直接将打包后的 blob link 扔到 src，脚本就会自动运行。

这一部分属于 JavaScript 基操，并没有什么难点。

依赖解析

难点在于，如何处理 TypeScript 脚本内的 static import 和 任何脚本内的 dynamic import。

比方说，我有一个 js 脚本去 await import 了一个 TS 脚本，如果我们不处理就会导致报错。

对于 static import，我的做法是在 traverse 的时候，先记录下所有的 import 的 source 和它们对应的 node，并且完成其它的擦除工作；traverse 一遍之后我只需要递归处理相关文件，然后直接修改对应的 source 再 generate。

同时，引入一个 Map 来记录所有已经转译的 URL -> blob URL 的映射。再处理到相同文件时，我们只需要返回同一个 blob URL，浏览器已有的 ESM 机制就能自动处理 cache/重复加载的问题。

动态 import 遇到的问题

其实解决 dynamic import / import.meta 也很简单，把它们换成一个自己生成的对象就可以了。由于 import 本身不是一个对象或者函数，它是一个 keyword，所以我们可以分情况替换成函数 / 对象。

问题是，我希望这个库不会污染全局环境，所以直接换成 window.__ts 这种方案是肯定不行的。

此外，用 window.__ts 也会导致时序问题——我的库初始化太慢。

那怎么样才能让不同模块共享同一个对象，没有时序问题且不污染全局呢？

匿名模块

解决方案也十分简单——创建一个匿名模块，导出 Promise.withResolvers()，然后需要用 __ts 的去等里面的 Promise，我在合适的场合 fulfill 它。

这样只要导入的 url 一致，这个对象就会在所有模块间共享，因而所有模块都拿得到 __ts 对象。
